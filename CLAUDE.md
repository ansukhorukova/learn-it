# Learning Time Tracker — контекст проєкту для Claude Code

Приватний застосунок для трекінгу часу навчання по тематичних бордах, з вкладеннями на кожній таскі. Двомовний (EN/UK), API-first, для подальшого розвитку поза MVP.

## Архітектура (API-first)

FE ніколи не звертається до бази напряму — тільки до власного BE API. BE — єдина точка авторизації й бізнес-логіки (замінює патерн RLS/security-definer функцій, специфічний для Supabase/Lovable). Це дає:
- один контракт (OpenAPI/REST), яким зможуть користуватись майбутні клієнти (мобільний застосунок, інтеграції);
- легку заміну провайдерів (Firebase Auth → інший auth, Postgres у Docker → керований Postgres) без переписування FE.

```
FE (React, Vite)  →  BE API (Node.js, REST)  →  PostgreSQL (Docker, локально)
                             ↓                              
                    Firebase Admin SDK ←→ Firebase Auth (верифікація токена)
                             ↓
                    S3-сумісне сховище (MinIO у Docker локально; R2/Blaze у продакшні)
```

### Файлове сховище — чому не Firebase Storage

З 3 лютого 2026 Firebase Storage вимагає платного плану Blaze навіть для мінімального використання в межах безкоштовної квоти (потрібна прив'язана картка). Тому файли вкладень йдуть через **S3-сумісний API**, а не Firebase Storage SDK:
- Локально — **MinIO** в Docker (сервіс `minio` у `docker-compose.yml`), повністю безкоштовно, без картки.
- У продакшні — Cloudflare R2 або Firebase Storage (Blaze), обидва зараз вимагають картку, але лишаються $0 у межах безкоштовної квоти; рішення відкладено до етапу деплою, бекенд працює з обома однаково через один і той самий S3-клієнт (зміна лише в env-змінних endpoint/ключів).
- Firebase лишається виключно для **Auth** — це безкоштовно без картки, без обмежень до 50K MAU.

## Локальна розробка — Docker

`docker-compose.yml` у корені піднімає чотири сервіси:
- **db** — `postgres:16-alpine`, том для персистентності, ініціалізаційні міграції.
- **minio** — S3-сумісне сховище файлів для локальної розробки (порт 9000 API, 9001 консоль), заміняє Firebase Storage локально (див. розділ "Файлове сховище").
- **backend** — Node.js (Express/Fastify) API, `depends_on: db, minio`, порт `4000`. Підключення до Postgres через `DATABASE_URL`, до сховища — через `STORAGE_ENDPOINT`/`STORAGE_ACCESS_KEY`/`STORAGE_SECRET_KEY` (S3 SDK). Верифікує Firebase ID token через Firebase Admin SDK (`FIREBASE_PROJECT_ID` + service account key з `.env`, не в git).
- **frontend** — React (Vite dev server), порт `5173`. Звертається лише до `VITE_API_URL` (backend), для логіну використовує Firebase client SDK (email+password), отриманий ID token кладе в `Authorization: Bearer` для кожного запиту до BE.

Firebase (безкоштовний Spark-план) потрібен лише для Auth — реальний проєкт у Firebase Console (або Firebase Local Emulator Suite для повністю офлайн-розробки, опційно на пізнішому етапі). Дані застосунку (borders/tasks/time_entries/attachments-метадані) живуть у Postgres у Docker, файли вкладень — у MinIO в Docker. Жодного хмарного акаунту чи картки не потрібно, щоб просто підняти й розробляти локально.

`.env.example` у корені фіксує всі змінні оточення без реальних значень (DATABASE_URL, FIREBASE_PROJECT_ID, FIREBASE_STORAGE_BUCKET, JWT/session секрети за потреби).

## API (обов'язково — контракт перш ніж код)

- REST, версійований (`/api/v1/...`), задокументований через OpenAPI (`openapi.yaml` у корені BE, оновлюється разом з кожним ендпоінтом).
- Кожен ресурс — стандартні CRUD-ендпоінти там, де це доречно: `/boards`, `/boards/:id/tasks`, `/tasks/:id/time-entries`, `/tasks/:id/attachments`, `/boards/:id/members`, `/tasks/:id/shares`.
- Авторизація — middleware-шар на BE: перевірка ролі (owner/collaborator/viewer) і приватності (time_entries тільки власні, крім агрегованих тоталів; visibility вкладень) відбувається в сервісному шарі BE перед кожним запитом до БД, не в самій БД.
- Помилки — консистентний формат (код, повідомлення, локалізований ключ повідомлення для FE).

## Екрани

1. **Sign in / sign up** (`/auth`) — email + пароль АБО Google (Firebase `GoogleAuthProvider`, popup-флоу) через Firebase Auth (FE напряму з Firebase client SDK; BE тільки верифікує ID token, не зберігає паролі й не розрізняє провайдера — верифікація й подальша авторизаційна логіка ідентичні для обох). При конфлікті (email вже зареєстрований іншим провайдером) — Firebase-помилка показується користувачу локалізованим повідомленням з пропозицією увійти правильним способом, без автоматичного лінкування акаунтів.
2. **Boards overview** (`/`) — сітка тематичних карток ("React", "SQL"), лічильники тасок і сумарний час. Створення/перейменування/видалення борду.
3. **Board view** (`/boards/$boardId`) — три колонки: Planned, In Progress, Done / PR merged. Таски — картки з назвою, сумарним часом, бейджами кількості вкладень. Переміщення таски між колонками (drag або контрол статусу), додавання/видалення тасок.
4. **Task panel** — бічна панель при кліку на таску:
   - **Час**: таймер старт/стоп + список сесій, форма ручного додавання/корекції запису (хвилини + опційна нотатка).
   - **Вкладення** ("хмарки"): згруповані по типу чіпи — файли (pdf/doc/зображення, для зображень — превʼю), посилання (заголовок + URL, відкриваються в новій вкладці), нотатки (короткий текст). Додаються інлайн, можна видалити.
5. **User profile** (`/profile`) — налаштування власного акаунту: редагування `public_name` (публічне ім'я, показується іншим у спільних бордах/шерингу замість системного `display_name`, якщо задане), список власних компетенцій (додавання з довідника або вручну, перемикач готовності викладати на кожній). `display_name` тут не редагується — лишається системним полем за контрактом AUTH-001…003. Перемикач мови на цьому екрані НЕ живе — він у верхньому меню (шапці), спільній для всіх автентифікованих екранів (див. розділ "Локалізація").

## Шеринг

- Можна поділитись **цілим бордом** або **окремою таскою** за email. Роль: viewer (тільки читання) або collaborator (може додавати таски/вкладення).
- **Прогрес завжди приватний.** Записи часу й таймери видно лише тому, хто їх залогував. На спільному борді кожен бачить свої тотали; опційний "team view" в шапці борду показує тотали по учасниках поруч (рахує BE через агрегуючий запит, віддає тільки суми — не чужі рядки), редагувати чужі записи не можна.
- **Статус таски** на спільному борді спільний (один Planned/In Progress/Done стан на всіх).
- **Видимість вкладення** налаштовується окремо: `private` (тільки я), `shared` (усі з доступом до борду/таски), `selected` (вибрані користувачі). Видимість показана на чіпі, змінюється з task panel.
- Секція "Shared with me" на boards overview — борди й таски, якими поділились з тобою.

## Поведінка

- Таймер — на рівні таски, лише один активний на користувача. Час рахується від збереженого `started_at` (зберігається на BE), а не від локального стану, тож закриття вкладки не губить прогрес. Зупинка — запит до BE, який пише рядок сесії.
- Тотали: таска → колонка → борд, плюс "this week" на boards overview — рахує BE.
- Переміщення в Done не видаляє історію трекінгу часу.

## Дані (PostgreSQL, доступ виключно через BE)

- `users` (id = Firebase UID, email, display_name, public_name, locale, last_sign_in_provider) — синхронізується з Firebase Auth при першому вході (апсерт, ідемпотентний за UID); `display_name` при створенні береться з Google-профілю, якщо вхід через Google, інакше з частини email до `@`, і надалі не перезаписується при повторних входах; `locale` — збережений вибір мови (розділ "Локалізація"); `last_sign_in_provider` — claim `firebase.sign_in_provider` (`password` | `google.com`) з декодованого ID token, оновлюється при **кожному** виклику `GET /api/v1/users/me` (на відміну від `display_name`), використовується вузькоспеціалізованим `GET /api/v1/auth/provider-hint` (без автентифікації, викликається лише зі шляху конфлікту при реєстрації, коли Firebase вже підтвердив існування email через `auth/email-already-in-use`) для показу точного повідомлення "цей email зареєстровано через Google" замість generic; ніколи не використовується і не повинен використовуватись на шляху sign-in (там анти-enumeration гарантія лишається незмінною — wrong-password і unknown-email недиференційовані); `public_name` — опційне поле, яке користувач редагує напряму з екрана профілю (розділ "Екрани" п.5), окреме від системного, незмінного після створення `display_name`; FE показує `public_name`, якщо задане, інакше фолбек на `display_name`, у будь-якому контексті, де мене бачить інший користувач (списки учасників борду, шеринг).
- `boards` (title, description, accent, owner_id)
- `tasks` (board_id, title, notes, status enum `planned | in_progress | done`, position, created_by)
- `board_members` (board_id, user_id, role enum `viewer | collaborator`)
- `task_shares` (task_id, user_id, role) — шеринг окремої таски без усього борду
- `time_entries` (task_id, user_id, started_at, ended_at, duration_seconds, note) — відсутній `ended_at` = таймер іде; BE віддає чужі entries тільки як агреговані суми, ніколи як рядки
- `attachments` (task_id, created_by, kind enum `file | link | note`, title, storage_path/url, mime_type, body, visibility enum `private | shared | selected`)
- `attachment_viewers` (attachment_id, user_id) — для visibility `selected`
- `competencies` (id, slug унікальний, is_active) — довідник передвизначених професій/навичок (напр. `mathematician`, `business_analyst`, `java_developer`), керується адміністративно поза релізами коду; відображувана назва — locale-ключ `competency.<slug>` в `locales/en.json`/`locales/uk.json`, за тим самим патерном, що вже застосований до лейблів статусу таски (enum-значення рендериться через словник, не зберігається як білінгвальний текст у БД).
- `user_competencies` (id, user_id, competency_id nullable FK → `competencies`, is_custom, custom_label nullable, willing_to_teach) — компетенції користувача; рівно одне з `competency_id`/`custom_label` заповнене залежно від `is_custom` (з довідника vs вільний текст, введений вручну, коли потрібної компетенції немає в списку — `custom_label` не перекладається, як user-generated контент типу назви борду/таски); `willing_to_teach` — прапорець "готовий викладати" на рівні конкретної компетенції користувача, не глобальний перемикач на `users`.

Міграції — **Knex** (query-builder + версіоновані файли міграцій, `backend/migrations/`, конфіг `backend/knexfile.js`, спільний інстанс — `backend/src/db/knex.js`). Обрано замість Prisma: легший рантайм у Docker/Alpine (без кодогенерації/бінарників при кожному білді), прямий контроль над SQL. Підключення — виключно через `DATABASE_URL` з env (ніякого хардкоду `db`/`localhost`), той самий код працює локально й проти Neon у продакшні. Авторизаційні перевірки — у сервісному шарі BE (`can_view_board`, `can_edit_board`, `can_view_task`, `can_view_attachment` як функції/сервіси в коді BE, аналог попередніх security-definer функцій, але на рівні застосунку, не БД).

Файли вкладень — MinIO локально / S3-сумісне сховище в продакшні; BE генерує signed/download URL через S3 SDK, FE ніколи не звертається до сховища напряму для читання/запису.

## Локалізація (обов'язково) — двомовний застосунок EN/UK з розширюваністю

- **Обидві мови обов'язкові з першого релізу**: англійська та українська. Жодна фіча не вважається завершеною, якщо в неї немає повних рядків для обох мов — це частина Definition of Done, а не етап "перекладемо потім".
- **Архітектура — під майбутні мови, а не лише під ці дві:**
  - Словники — окремі файли per-locale: `locales/en.json`, `locales/uk.json`. Додавання нової мови в майбутньому = новий файл `locales/{code}.json` + одна строка реєстрації в списку підтримуваних локалей, без змін у компонентах.
  - Ніде в коді не повинно бути `if (lang === 'uk')`-логіки, специфічної для конкретної мови, окрім самої утиліти плюралізації/форматування — вона приймає правило форми множини як параметр з locale-конфігу, а не хардкодить перевірку на "uk".
  - Ключі перекладів — за змістом (`board.create.title`), не за мовою.
  - API-помилки й повідомлення від BE також мають локалізований ключ, а не готовий текст — переклад формує FE зі свого словника.
- **Визначення мови за замовчуванням:** за browser locale користувача при першому вході, з можливістю ручного перемикання; збережений вибір персистить у `users`.
- **Плюралізація:** ICU-подібний підхід (EN: one/other, UK: one/few/many/other), не єдина захардкожена логіка.
- Формати дати/часу — locale-aware (`Intl.DateTimeFormat`), не фіксований формат.
- Перемикач мови — у верхньому меню (шапці, `AppHeader`), поруч з посиланням на профіль, видимий на кожному автентифікованому екрані (рішення 2026-08-24, AUTH-008; початково планувався всередині `/profile`, перенесено до шапки, щоб перемикання мови не вимагало переходу на окремий екран).

## Стилізація

Warm dark surfaces, один amber-акцент для активних таймерів, пейринг шрифтів Sora/Manrope, усе через design tokens (без хардкоду кольорів). Кожен роут має власні head-метадані (title, description, og tags).

## Деплой (production)

Локальний Docker — тільки для розробки. Продакшн-ціль (без архітектурних змін, лише інша конфігурація того самого коду):

- **Frontend** → Firebase Hosting (той самий Firebase-проєкт, що й для Auth).
- **Backend** → Google Cloud Run — той самий Docker-образ, що й локально; підключається до продакшн-БД через `DATABASE_URL` і до production Firebase service account через секрет, а не через змінну оточення з ключем у відкритому вигляді.
- **Database** → Neon (безкоштовний керований Postgres) — локальний Docker `db`-сервіс лишається лише для dev/тестів; той самий образ backend у продакшні просто отримує інший `DATABASE_URL`.
- **Файлове сховище** → Cloudflare R2 або Firebase Storage (Blaze) — обидва зараз вимагають прив'язану картку, але лишаються $0 у межах безкоштовної квоти (R2: 10GB/міс; Blaze: 5GB-місяців). Рішення відкладено до моменту деплою — і R2, і Firebase Storage сумісні з тим самим S3-клієнтом на BE, що й MinIO локально, тож заміна — це лише env-змінні, без правок коду.
- CI (пізніше): збірка backend/frontend образів → деплой backend на Cloud Run, frontend на Firebase Hosting, міграції БД проти Neon перед релізом бекенду.

Це навмисно винесено окремо від "Поза межами цього етапу" — деплой не є фічею продукту, але команда має знати цільову інфраструктуру заздалегідь, щоб не закладати в код нічого, що прив'язує до одного лише локального Docker (напр. хардкод `localhost` замість змінних оточення).

## Поза межами цього етапу

Публічні посилання для незареєстрованих, коментарі/обговорення, нотифікації та email-запрошення для людей без акаунту, синхронізація з календарем, графіки складніші за прості тотали. Сам процес налаштування CI/CD — окрема задача пізніше (цільова інфраструктура вже зафіксована вище в "Деплой").
